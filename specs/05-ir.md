# 05 — Intermediate Representations

## Overview

Kali uses a three-level IR pipeline. Each level makes progressively more concrete decisions about memory layout, control flow, and WASM representation.

```
Typed AST → HIR → MIR → LIR → WASM
```

## HIR — High-Level IR

### Purpose
- Desugared, normalized representation of the source
- Close to source semantics but without syntactic sugar
- All name resolution completed, all types resolved
- Input to optimization passes that reason about program semantics

### Desugaring
- `for-of` → iterator protocol calls
- Destructuring → sequential property access / index
- Optional chaining → conditional expressions
- Nullish coalescing → null check conditionals
- `class` → constructor function + prototype setup
- `async/await` → state machine (coroutine lowering)
- Generators → state machine
- Spread → explicit iteration
- Default parameters → conditional assignment
- Template literals → string concatenation calls

### Node Types
```rust
enum HirExpr {
    Literal(TypedLiteral),
    LocalGet(LocalId),
    LocalSet(LocalId, Box<HirExpr>),
    PropertyGet(Box<HirExpr>, PropertyKey),
    PropertySet(Box<HirExpr>, PropertyKey, Box<HirExpr>),
    Call(Box<HirExpr>, Vec<HirExpr>),
    Construct(Box<HirExpr>, Vec<HirExpr>),
    BinaryOp(BinOp, Box<HirExpr>, Box<HirExpr>),
    UnaryOp(UnOp, Box<HirExpr>),
    Closure(ClosureId, Vec<CapturedVar>),
    // ... etc
}
```

Each HIR node carries its resolved `TypeId`.

## MIR — Mid-Level IR

### Purpose
- Explicit memory layout decisions
- Objects classified as static-layout (struct-like) or dynamic (hash map)
- Ownership annotations on every value
- SSA form for efficient analysis and optimization
- Stack vs heap allocation decided

### Memory Layout Classification

```rust
enum ObjectLayout {
    /// All properties known at compile time, fixed offsets
    Static {
        fields: Vec<(InternedString, TypeId, u32 /* offset */)>,
        size: u32,
        align: u32,
    },
    /// Some properties unknown or dynamic keys used
    Dynamic {
        known_fields: Vec<(InternedString, TypeId, u32)>,
        /// Fallback hash map for unknown properties
        has_dynamic_slot: bool,
    },
    /// Fully dynamic — e.g., used as a dictionary, computed keys
    HashMap,
}
```

### When Static Layout Applies
- Object literal where all properties are known
- Class instances where no dynamic property access occurs (no `obj[expr]` with non-literal key)
- No `delete` on the object
- No `Object.defineProperty` or `Proxy` usage
- Not passed to a function that expects `any` or uses dynamic access

### When Dynamic Layout Is Forced
- Property access with computed key: `obj[variable]`
- `delete obj.prop`
- Use of `Proxy`
- Object spread from unknown source
- `Object.keys()`, `for...in` iteration
- Assignment to `any` or passing to untyped function

### SSA Form
- All temporaries are SSA variables
- Phi nodes at control flow joins
- Enables standard optimizations: constant propagation, dead code elimination, copy propagation

### Ownership Annotations
```rust
enum Ownership {
    /// Value lives on the stack, no cleanup needed
    Stack,
    /// Unique owner, heap-allocated, freed when owner scope exits
    OwnedHeap,
    /// Shared reference, reference-counted (Rc)
    Shared,
    /// Borrowed reference (no ownership transfer, must not outlive source)
    Borrowed,
}
```

See [specs/06-memory.md](06-memory.md) for the analysis that assigns ownership.

## LIR — Low-Level IR

### Purpose
- Directly maps to WASM instructions
- All types are WASM value types (i32, i64, f64, funcref, externref)
  - Note: `f32` is not used — all JS `number` values use `f64`; `Float32Array` operations use `f64` with narrowing stores
- All memory accesses are explicit load/store with offsets
- Linear memory layout finalized
- Function table indices resolved

### Node Types
```rust
enum LirInst {
    // Memory
    I32Load(MemArg),
    I64Load(MemArg),
    F64Load(MemArg),
    I32Store(MemArg, LirValue),
    I64Store(MemArg, LirValue),
    F64Store(MemArg, LirValue),
    // Arithmetic
    I32Add(LirValue, LirValue),
    F64Mul(LirValue, LirValue),
    // Control flow
    Block(BlockId),
    Loop(LoopId),
    BrIf(LirValue, LabelId),
    Br(LabelId),
    // Calls
    Call(FuncIdx, Vec<LirValue>),
    CallIndirect(TableIdx, LirValue, Vec<LirValue>),
    // etc
}
```

### Transformations from MIR
- Object field access → `load` at computed offset
- Rc increment/decrement → calls to runtime ref-count functions
- String operations → calls to runtime string functions
- Closure creation → struct allocation + function table entry
- Dynamic dispatch → `call_indirect` through function table

## Value Representation

The IR must handle the spectrum from fully-typed to fully-dynamic values:

```rust
enum ValueRepr {
    /// Known type, unboxed, native WASM value
    Unboxed { wasm_type: WasmValType },
    /// Known type, struct layout in linear memory
    Struct { layout: ObjectLayout },
    /// Unknown type, tagged union (NaN-boxing or tagged pointer)
    Tagged,
    /// Fully dynamic, hash map representation
    Dynamic,
}
```

### NaN-Boxing for Tagged Values
When a value's type is unknown at compile time, use NaN-boxing in a 64-bit float:
- Doubles: stored directly
- Integers (i31): tagged in NaN payload
- Pointers: tagged in NaN payload (assuming the canonical early-phase `wasm32` address space)
- Booleans, null, undefined: sentinel NaN values

If Kali later gains a non-`wasm32` backend, tagged representation may need a different layout. That change should be treated as a target-profile extension, not as an implicit change to this IR contract.

### Representation Transitions
The compiler inserts boxing/unboxing at boundaries between typed and untyped code:
- Calling an untyped function from typed code → box arguments
- Receiving results from untyped code → unbox (with runtime type check)
- These transitions are flagged in diagnostics so users know where performance degrades

## IR Metadata

All IR levels carry:
- **Source spans** for error reporting at any stage
- **Type information** for debugging and verification
- **Effect annotations** propagated from the type checker
- **Optimization hints** (e.g., hot/cold branch annotations from profile data)

## Validation

Each IR level has a validator that checks internal consistency:
- HIR: all references resolve, types are consistent
- MIR: SSA property holds, ownership is consistent, memory layouts are valid
- LIR: WASM type rules are satisfied, memory accesses are in bounds (where provable)

These validators run in debug builds and can be enabled in release with `--validate-ir`.
